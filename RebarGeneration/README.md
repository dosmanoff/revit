# RebarGeneration

Универсальная оболочка для массовой генерации арматуры в Revit: агент пишет
**задание**, плагин разворачивает его в **наборы** и кладёт в модель **одним
шагом отмены**.

Разбор проблемы, замеры и план — в [`ARCHITECTURE.md`](ARCHITECTURE.md).

---

## Зачем

Поштучное создание арматуры через MCP-инструменты стоит ~3.5 с на стержень
(замер по журналу мутаций: 1647 стержней = 5685 с). Доминирует не Revit, а
полный round-trip LLM на каждый стержень. Плагин убирает LLM из внутреннего
цикла: одно задание — один вызов — одна группа транзакций.

## Что универсально, а что нет

Универсальны **каркас и протокол**, а не геометрия:

```
Core (host-agnostic)         Генераторы (host-specific)
├── контракт задания         ├── polyline  — кривые + раскладка (универсальный запасной путь)
├── валидация до транзакции  ├── footing   — сетки подошвы по габариту
├── KeyIndex (идемпотентность)   └── (дальше — обёртки над SlabReinforcer /
├── TypeCache                     WallReinforcer / ColumnReinforcer)
├── транзакции и чанкинг
├── подавление warnings
├── отчёт и журнал
```

Попытка сделать универсальной саму геометрию даёт либо общий знаменатель
(прямые стержни в коробке), либо объединение трёх схем с гигантским `switch`.
Поэтому предметные генераторы остаются раздельными, а `polyline` закрывает всё,
для чего своего генератора нет.

## Как это вызывает агент

Публичная дверь одна и на строках — **JSON внутрь, JSON наружу**:

```csharp
Api.Run(doc, jobJsonPath)      // выполнить задание
Api.DryRun(doc, jobJsonPath)   // построить и откатить; отчёт настоящий
Api.RunJson(doc, jobJson)      // то же, но задание строкой
Api.Validate(jobJsonPath)      // проверить схему без Revit
Api.Describe(doc, "id1,id2")   // контекст для написания задания
Api.Info()                     // версия, схемы, список генераторов
```

Сигнатура выбрана так намеренно: агент вызывает плагин из pyRevit Routes
`/exec`, то есть из IronPython, и любой .NET-генерик на границе
(`IEnumerable<ElementId>`, `IDictionary<,>`) превращается в возню с маршалингом.
JSON-строка убирает проблему целиком.

Из `/exec` после установки:

```python
import clr
clr.AddReference("RebarGeneration")      # ПО ИМЕНИ: сборка уже в AppDomain,
from RebarGeneration import Api          # файловой пробы нет
out["report"] = Api.Run(doc, r"C:\work\fdn-job.json")
```

`clr.AddReference` здесь обязателен: манифест `.addin` загружает сборку в
процесс, и `System.Type.GetType("RebarGeneration.Api, RebarGeneration")` её
находит, но синтаксис `from … import` у IronPython работает только по
зарегистрированной ссылке. Аргумент — **имя сборки, не путь**: она уже
загружена, поиск идёт по AppDomain.

Тот же фасад бесплатно даёт три транспорта: `/exec` сегодня, команда в
commandset для MCP-инструмента завтра, кнопки на ленте для человека.

> **Важно: не грузить сборку с `G:\` через `clr.AddReferenceToFileAndPath`.**
> Загрузка .NET-сборки с диска, синхронизируемого Google Drive, блокирует
> обработчик Routes — Revit перестаёт отвечать на запросы моста (проверено,
> получено на живом сеансе 2026-08-02). Правильный путь — установить плагин
> в `%APPDATA%` через `deploy/install.ps1`; после этого тип доступен по имени,
> как у остальных плагинов репозитория.

## Задание

```jsonc
{
  "schema": "rebar-job-1.0",
  "units": "mm",                       // конвертация в футы ровно одна, на границе
  "dryRun": false,
  "policy": {
    "onExistingKey": "skip",           // skip | replace | error
    "reuseStandardShapes": true,
    "suppressWarnings": true,
    "includeIds": false                // карта key→id уходит в файл, а не в контекст
  },
  "defaults": { "barType": "#5", "cover": 75 },
  "groups": [
    {
      "key": "FDN:F1:MAT",             // адресует НАБОР, не отдельный стержень
      "generator": "footing",
      "hostId": 123456,
      "bottom": { "x": { "spacing": 300 }, "y": { "spacing": 300 } }
    },
    {
      "key": "PILE:P3:TIES",
      "generator": "polyline",
      "hostId": 123457,
      "barType": "#4",
      "hooks": { "start": "135", "end": "135" },
      "curves": [[[0,0,1000],[600,0,1000],[600,600,1000],[0,600,1000],[0,0,1000]]],
      "count": 14, "spacing": 250, "distribution": [0,0,1]
    }
  ]
}
```

Готовые примеры — в [`samples/`](samples).

## Решения, которые стоит знать

**Транзакции.** Весь прогон — один `TransactionGroup`, то есть **один шаг Revit
Undo**. Внутри — по одной `Transaction` на **хост**. Критерий дробления именно
хост, а не количество: падение одного элемента откатывает только его армирование.
`policy.maxSetsPerTransaction` — вторичный предохранитель от разбухания буфера
отмены.

**Наборы, а не стержни.** `SetLayoutAsNumberWithSpacing` кладёт полосу одним
элементом: 1000 стержней плиты — это 20–40 элементов. Спецификации считают
правильно, теги и MRA работают, модель весит на два порядка меньше.

**Идемпотентность.** Индекс `key→ElementId` строится **одним** проходом в начале
прогона. Формат ключа совпадает с revit-context (`CTX_Key`, иначе токен
`[[ctx:KEY]]` внутри Comments **без затирания** остального текста — там живут
марки вида «8#7 [1]»). Повторный прогон по тем же ключам ничего не дублирует.

**Отказ группы не рвёт прогон.** Уже созданные этой группой элементы удаляются,
группа помечается `failed`, остальные продолжают. Частично собранная группа хуже
отсутствующей.

**Сухой прогон настоящий.** Строится всё, затем `TransactionGroup.RollBack()`.
Отчёт содержит реальные количества и реальные ошибки, модель не меняется.

**Отчёт дешёвый в токенах.** Агрегаты и по строке на группу. Списки `ElementId`
не возвращаются, если не попросить явно; карта `key→ElementId` пишется в файл.

## Сборка

```bash
dotnet build src/RebarGeneration/RebarGeneration.csproj -c "Release R2025"
dotnet test  tests/RebarGeneration.Contracts.Tests/RebarGeneration.Contracts.Tests.csproj
```

Конфигурации: `Debug`/`Release` (CI собирает ими, целевой Revit 2025) плюс
`Debug|Release R2025` и `R2026`. Revit API подключён reference-only пакетами
`Nice3point.Revit.Api.*`, поэтому проект собирается и на Linux-раннере CI.

Тесты покрывают **чистую** часть (48 тестов): контракт и разбор задания,
единицы, нормаль плоскости, раскладка, формат ключа, валидатор. Revit для них
не нужен.

## Установка

```powershell
pwsh deploy/install.ps1 -RevitVersion 2025
```

Revit должен быть закрыт — он держит DLL заблокированной. Скрипт проверяет это
и отказывается работать вслепую.

После установки: вкладка **Smart Tools** → панель **Rebar Generation** →
кнопки **Run Job** / **Dry Run**. Регистрация `.addin` нужна не только ради
кнопок: именно она загружает сборку в процесс Revit, благодаря чему агент
достаёт `RebarGeneration.Api` из `/exec` по имени типа.

## Замеры на живой модели

Проверено 2026-08-02 на `7-15 Terrace View Avenue_R3` (1358 существующих
стержней, Revit 2025.4), вызовом из pyRevit Routes `/exec`. Оба прогона —
`Api.DryRun`; счётчик арматуры до и после совпал, то есть откат отработал.

| Путь | На элемент | Экстраполяция на 1000 стержней |
| --- | --- | --- |
| Поштучный `create_rebar` (замер по журналу) | **3450 мс** | ~57 мин |
| Плагин, **отдельные** элементы (120 шт., 1 транзакция) | **25.5 мс** | ~26 с |
| Плагин, **наборами** (180 стержней = 3 элемента) | 1080 мс на прогон | ~1–2 с |

**135×** на худшем случае — когда наборы неприменимы и каждый стержень
отдельный элемент. С наборами разрыв на два порядка больше.

Побочно подтвердилось, что работает как задумано:

- `WarningSwallower` перехватил «Rebar is placed completely outside of its host»
  (×16) и вынес в отчёт **вместо модального диалога** — прогон не встал;
- `KeyIndex` нашёл в модели реальную неоднозначность: ключ `colcage` носят
  несколько элементов;
- обе группы на одном хосте легли в **одну** транзакцию, как и задумано.

Те 16 предупреждений — следствие документированного ограничения: тест гнал
стержни по габаритному боксу плиты, а её реальный контур прямоугольником не
является. Ровно тот случай, для которого предназначен `polyline`.

Всё проверено на той же живой модели. Тестовые стержни удалены, счётчик

## Состояние

Реализовано, собрано, проверено на живой модели. Известные ограничения:

- **Revit 2026**: используется перегрузка `Rebar.CreateFromCurves` с
  `RebarHookOrientation`, которая там помечена устаревшей в пользу
  `BarTerminationsData`. Собирается и работает, но при переходе на 2026 это
  надо переписать. Ветку под новый API намеренно не добавлял: проверить её без
  Revit 2026 всё равно нечем, а непроверенный `#if` хуже честного
  предупреждения компилятора.
- **`footing`** раскладывает по габариту в координатах модели: подошва
  предполагается прямоугольной и выровненной по осям. Повёрнутая или
  непрямоугольная — через `polyline`.
- Наборы переменной длины (`RebarFreeFormAccessor`) не поддержаны.
- Обёрток над `SlabReinforcer` / `WallReinforcer` / `ColumnReinforcer` нет: они
  работают и вызываются из `/exec` напрямую.
- Отдельного файла JSON-схемы задания нет — контракт живёт в этом README и в
  типах `RebarGeneration.Contracts`.

Не сделано: обёртки-генераторы над `SlabReinforcer` / `WallReinforcer` /
`ColumnReinforcer` (они уже работают самостоятельно и вызываются напрямую),
`FootingGenerator` для повёрнутых и непрямоугольных подошв (для них — `polyline`).
