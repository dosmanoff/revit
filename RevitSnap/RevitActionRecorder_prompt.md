# Промпт для Claude Code: плагин RevitActionRecorder

> Скопируй всё, что ниже разделителя, в Claude Code как первое сообщение.

---

## Задача

Построй production-ready аддин для Autodesk Revit — **RevitActionRecorder**. Его назначение: полностью, без потерь фиксировать работу инженера в Revit в машиночитаемом JSON, чтобы по этой записи LLM-агент мог восстановить методику работы и воспроизвести её.

Записывать нужно три слоя:

1. **Поток событий** — что пользователь делал, в каком порядке, с какими параметрами, включая реакцию на предупреждения.
2. **Полные снапшоты состояния модели** «до» и «после» сессии — абсолютно все объекты со всеми параметрами, включая оформительские настройки.
3. **Структурированный дифф** между снапшотами.

Всё это — не для человека, а для машинного разбора. Формат первичен, красота UI вторична.

## Технический стек

- **C# / .NET 8** (`net8.0-windows`) — Revit 2025 и 2026 оба на .NET 8, TFM общий.
- **Целевые версии: Revit 2025 и Revit 2026.** Один solution, две конфигурации сборки: `Debug R2025`, `Release R2025`, `Debug R2026`, `Release R2026`. Константы условной компиляции `REVIT2025` / `REVIT2026`.
- **Revit API** подключай через NuGet-пакеты `Nice3point.Revit.Api.RevitAPI`, `Nice3point.Revit.Api.RevitAPIUI`, `Nice3point.Revit.Api.AdWindows` соответствующих версий (`2025.*` / `2026.*`), с `ExcludeAssets="runtime"` / `<Private>false</Private>`, чтобы API-сборки не копировались в выход.
- **Сериализация:** `System.Text.Json`, строго потоковая через `Utf8JsonWriter` напрямую в `GZipStream` → `FileStream`. Не строй объектное дерево всей модели в памяти.
- Никаких сторонних зависимостей сверх перечисленного без явной необходимости; если что-то нужно — сначала обоснуй.

## Структура решения

```
RevitActionRecorder.sln
  src/
    RevitActionRecorder/            — аддин (зависит от Revit API)
      Application/                  — IExternalApplication, лента, команды
      Recording/                    — подписки на события, EventBus, JSONL writer
      Snapshot/                     — обход модели, экстракторы
      Imaging/                      — экспорт PNG через ExternalEvent
      Configuration/                — чтение/запись config.json
      Infrastructure/               — логирование, пути, безопасные обёртки
    RevitActionRecorder.Model/      — POCO-модели JSON-схемы, БЕЗ ссылок на Revit API
    RevitActionRecorder.Diff/       — движок сравнения снапшотов, БЕЗ ссылок на Revit API
  tests/
    RevitActionRecorder.Diff.Tests/ — xUnit, чистые unit-тесты диффа на синтетических JSON
  deploy/
    RevitActionRecorder.2025.addin
    RevitActionRecorder.2026.addin
    install.ps1
  README.md
```

Ключевое требование к архитектуре: **`Model` и `Diff` не должны ссылаться на Revit API.** Это делает дифф-движок и схему тестируемыми без Revit. Аддин заполняет POCO из Revit и отдаёт их сериализатору.

## Режим работы и UI

Вкладка ленты **«Recorder»**, панель с кнопками:

- **Start recording** — создаёт папку сессии, снимает полный снапшот «до», экспортирует PNG эталонных видов, включает подписки на события.
- **Stop recording** — снимает снапшот «после», экспортирует PNG, считает дифф, отписывается, показывает итоговое окно с путём к папке сессии и краткой статистикой.
- **Snapshot now** — промежуточный полный снапшот без остановки записи.
- **Mark moment** — диалог с текстовым комментарием пользователя + PNG активного вида; пишется отдельным событием в поток. Это способ вручную отметить «вот здесь важное решение».
- **Open session folder**, **Settings**.

Состояние кнопок должно корректно отражать, идёт запись или нет. Кнопки записи неактивны, если нет открытого документа.

## Слой 1: поток событий (events.jsonl)

Одна строка JSON на событие, без переносов внутри строки. Подписки:

| Источник | Событие | Что извлекать |
|---|---|---|
| `ControlledApplication` | `DocumentChanged` | ядро: см. ниже |
| `ControlledApplication` | `FailuresProcessing` | текст ошибок/предупреждений, серьёзность, ID элементов, выбранное разрешение |
| `UIApplication` | `DialogBoxShowing` | `DialogId`, `HelpId`, текст (если доступен), результат |
| `UIApplication` | `ViewActivated` | предыдущий и новый вид |
| `UIApplication` | `SelectionChanged` | (Revit 2024+) ID и категории выбранных элементов |
| `ControlledApplication` | `DocumentOpened`, `DocumentClosing`, `DocumentSaved`, `DocumentSavedAs`, `DocumentSynchronizedWithCentral`, `DocumentPrinted` | путь, признак центрального файла |
| `Autodesk.Windows.ComponentManager` | `ItemExecuted` | имя и ID нажатой кнопки ленты |

### DocumentChanged — что писать

- `GetTransactionNames()` — человекочитаемые подписи стека Undo, это главный смысловой ярлык события.
- `Operation` — обязательно писать в лог и **фильтровать undo/redo**: в итоговом «чистовом» потоке отменённые действия должны быть помечены, чтобы агент видел финальный метод, а не метания. Не удаляй их, а маркируй флагом `undone: true`.
- `GetAddedElementIds()` / `GetDeletedElementIds()` / `GetModifiedElementIds()`.
- Для добавленных и изменённых — раскрывай элемент: `Id.Value`, `UniqueId`, категория, класс, имя типа и семейства, уровень, воркcет.
- **Для изменённых — дельта по параметрам** (см. ниже про теневой кэш).

Известная особенность API: при выходе из режима Edit Assembly с отменой событие приходит с пустыми списками ID. Обрабатывай такой случай, опираясь на `GetTransactionNames()`, и не падай.

### Корреляция команды и транзакции

`ComponentManager.ItemExecuted` срабатывает **до** транзакции. Держи «последнюю нажатую команду» с меткой времени и привязывай её к ближайшему последующему `DocumentChanged`, если разрыв меньше настраиваемого порога (по умолчанию 2000 мс). Иначе поле `cmd` остаётся null. Подписка на `ComponentManager` недокументирована — оберни её в try/catch и корректно работай при её отсутствии.

### Теневой кэш параметров

`DocumentChanged` сообщает, что элемент изменился, но **не говорит, какое поле**. Решение:

- Снапшот «до» одновременно служит теневым кэшем: `ElementId → словарь параметров`.
- На каждом `DocumentChanged` перечитывай только изменённые ID, сравнивай с кэшем, пиши дельту вида `{param, from, to}`, затем обновляй кэш.
- Кэш держи в памяти в компактном виде (не POCO целиком, а хеш/словарь строк) — модель может быть на сотни тысяч элементов.

### Пример строки events.jsonl

```json
{"schema":1,"seq":312,"t":"2026-07-25T14:03:11.482+03:00","kind":"doc_changed","op":"TransactionCommitted","undone":false,"txn":["Разместить стену"],"cmd":{"id":"ID_OBJECTS_WALL","title":"Стена"},"view":{"id":1204,"name":"1 этаж"},"added":[{"id":845201,"uid":"...","cat":"Стены","type":"Базовая стена: Внутренняя 200","level":"Уровень 2"}],"modified":[{"id":845100,"cat":"Стены","params":[{"name":"Смещение сверху","bip":"WALL_TOP_OFFSET","from":"0","to":"-150"}]}],"deleted":[]}
```

## Слой 2: полный снапшот

**Режим — «абсолютно всё, без фильтров».** Снимай всё перечисленное ниже. Производительность решай инженерно (стриминг, gzip, отсутствие лишних аллокаций), но не за счёт урезания состава данных.

### Экземпляры и типы

Обход `FilteredElementCollector` дважды: `WhereElementIsNotElementType()` и `WhereElementIsElementType()`. По каждому элементу:

- `Id.Value` (в Revit 2024+ это `long`, `IntegerValue` устарел — не используй), `UniqueId`, `Name`
- Категория и подкатегория, `.NET`-класс элемента
- `GetTypeId()`, имя семейства и типоразмера
- Уровень, воркcет, вариант проектирования, стадия создания/сноса, группа, сборка
- **Все параметры** через `GetOrderedParameters()` + `Parameters`: имя, `BuiltInParameter` (если есть), GUID для общих параметров, `StorageType`, спецификация `Definition.GetDataType()` (ForgeTypeId), сырое значение, `AsValueString()`, `IsReadOnly`, `IsShared`
- `BoundingBox` (в координатах модели), `Location` — точка или кривая с координатами
- Детерминированный **хеш геометрии**: SHA-256 по тесселированной геометрии (`get_Geometry` с `DetailLevel.Fine`). Сырую геометрию не сохраняй — только хеш, иначе файл станет неуправляемым. Хеш даёт возможность увидеть «геометрия изменилась», не храня её.

### Оформительский слой — снимать полностью

Это отдельное явное требование, не пропускай ничего:

- **По каждому виду:** тип вида, шаблон вида, `Scale`, `DetailLevel`, `DisplayStyle`, дисциплина, `Discipline`, подложка, ориентация, область подрезки и её видимость, диапазон вида (`GetViewRange`) для планов, `GetNonControlledTemplateParameterIds`
- **Переопределения графики:** `GetCategoryOverrides` по всем категориям, `GetCategoryHidden`, `GetElementOverrides` по всем элементам, у которых они заданы, `GetFilters` + `GetFilterOverrides` + `GetFilterVisibility` + `GetIsFilterEnabled`. Разворачивай `OverrideGraphicSettings` во все поля: цвета и веса линий проекции/разреза, образцы штриховки поверхности и разреза, прозрачность, полутон, детализация
- **Стили объектов:** `Document.Settings.Categories` рекурсивно по подкатегориям — вес линий проекции и разреза, цвет, образец линий, материал
- **Ресурсы оформления:** `LinePatternElement`, `FillPatternElement`, `Material` + `AppearanceAssetElement`, `TextNoteType`, `DimensionType`, типы марок, типы линий
- **Листы:** `ViewSheet` + все `Viewport` (позиция, тип, положение подписи), основная надпись, ревизии (`GetAllRevisionIds`, `GetAdditionalRevisionIds`)
- **Спецификации:** `ViewSchedule.Definition` — поля и их порядок, фильтры, сортировка и группировка, форматирование, признак итогов
- **Легенды**, **шаблоны видов** отдельным разделом

### Настройки проекта

`ProjectInformation`, единицы измерения (`Document.GetUnits()` с обходом `UnitUtils.GetAllMeasurableSpecs()` и `FormatOptions` по каждой), уровни и оси, стадии, воркcеты (`FilteredWorksetCollector`), варианты проектирования, связи (`RevitLinkType`/`RevitLinkInstance` с путями и типом привязки), общие координаты (`ActiveProjectLocation.GetProjectPosition()`), настройки печати, глобальные параметры.

### Предупреждения модели

`Document.GetWarnings()` — полный список с текстом, серьёзностью и ID участвующих элементов. Это очень ценный сигнал: разница в предупреждениях «до/после» показывает, что метод чинит, а что ломает.

### PNG-снимки

В конфиге — список видов (точные имена и/или regex-шаблон). При снапшотах «до» и «после», а также по кнопке Mark moment, экспортируй их через `Document.ExportImage`. **Критично:** `ExportImage` нельзя вызывать из обработчика события. Складывай запросы в очередь и разгребай через `ExternalEvent` или `Idling`. Кладём в `shots/before/`, `shots/after/`, `shots/marks/`.

## Слой 3: дифф

Отдельный проект без зависимости от Revit. Вход — два файла снапшота, выход — `diff.json`:

- `added` / `removed` — списки элементов с их идентификацией
- `modified` — по каждому элементу список изменённых полей `{path, from, to}`, включая параметры, переопределения графики, настройки видов
- отдельные секции для диффа настроек проекта, стилей объектов и предупреждений
- сводка сверху: сколько добавлено/удалено/изменено по категориям

Сопоставление элементов — по `UniqueId` в первую очередь, `Id` как запасной вариант.

## Жёсткие ограничения

Это правила, нарушение которых считается багом:

1. **Аддин никогда не модифицирует документ.** Ни одной транзакции на запись.
2. **Весь Revit API — только в главном потоке.** Извлечение данных из Revit-объектов синхронно; в фоновый поток можно отдавать только уже извлечённые POCO/строки. Запись `events.jsonl` — через `Channel<T>` и фоновый писатель.
3. **Аддин не должен ронять Revit.** Каждый обработчик события целиком в try/catch, ошибки — в `log.txt`, наружу не пробрасываются.
4. `DocumentChanged` — read-only, никаких попыток изменить документ внутри.
5. В `OnShutdown` отписывайся от всех событий и корректно закрывай файлы.
6. Корректная работа при нескольких открытых документах: запись привязана к конкретному документу, события чужих документов игнорируются.
7. Не мешать синхронизации с центральным файлом.
8. Никаких сетевых обращений, никакой телеметрии.
9. Долгие операции (снапшот) — с индикатором прогресса и возможностью отмены, UI не должен выглядеть зависшим.

## Конфигурация

`config.json` рядом со сборкой + окно Settings. Поля минимум: корневая папка вывода, список видов для PNG и их разрешение, порог корреляции команды и транзакции (мс), включение gzip, включение хеша геометрии, уровень логирования.

## Порядок работы

Делай поэтапно, после каждого этапа — рабочая сборка и краткий отчёт, не переходи дальше без моего подтверждения:

1. **Каркас.** Solution, проекты, мультиконфигурация R2025/R2026, `.addin`-манифесты, `install.ps1`, лента с кнопками-заглушками. Проверка: аддин грузится в обоих Revit, вкладка видна.
2. **Поток событий.** Все подписки, `events.jsonl`, корреляция команд, обработка undo/redo. Ещё без дельт по параметрам.
3. **Снапшот.** Экстракторы экземпляров, типов, параметров, геометрии; потоковая запись в gzip.
4. **Оформительский слой снапшота.** Виды, переопределения, стили объектов, ресурсы, листы, спецификации, настройки проекта, предупреждения.
5. **Теневой кэш и дельты параметров** в потоке событий.
6. **Дифф-движок** + unit-тесты на синтетических снапшотах.
7. **PNG-экспорт** через ExternalEvent, кнопка Mark moment.
8. **Настройки, README, полировка**, прогон на реальной модели, замер времени и размера снапшота.
